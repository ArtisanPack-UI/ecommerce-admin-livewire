# `artisanpack-ui/ecommerce-admin-livewire` 1.0.0 release-readiness audit

- **Audited:** branch `release/1.0` at `c0f545c`, against engine `artisanpack-ui/ecommerce` `main` at `7e0f1a4` (tag `v1.0.0`).
- **Date:** 2026-10-05
- **Verdict:** **not releasable yet.**

The package was written against the pre-1.0 engine. Engine 1.0 made several breaking changes:

- Every table now has the `ecommerce_` prefix.
- License keys are encrypted.
- `warehouse_id` defaults to `0`.
- Every built-in now declares a config schema.
- Refunds are capped per line.
- GraphQL is now optional.

Together these break most screens. CI is also broken: it clones an engine branch that no longer exists. The authorization model, ID scoping, CSRF, `#[Locked]` usage, action tokens, XSS escaping, and translation parity are all solid. See [Coverage](#coverage-checked-and-fine) at the end.

## How to use this document (for the implementing agent)

1. **Read Section 0 first.** All owner decisions are already answered there. Apply them as written, and don't ask the owner again.
2. Work **in batch order** (A → K). Batch A makes the suite runnable. Batch B fixes the engine-compat blockers that cause most failures. Later batches assume both are done.
3. **One branch, one PR.** Create `fix/1.0-release-readiness` from `release/1.0`, commit once per batch (or per item when an item is large), and open a single PR into `release/1.0`. Don't open one PR per batch.
4. **Code style.** This package uses WordPress-style spacing. **Never run `vendor/bin/pint`.**
   - Format with `./vendor/bin/php-cs-fixer fix`, then check with `composer lint`.
   - If Pint was run by accident, delete `.php-cs-fixer.cache` and run php-cs-fixer again.
   - Use Yoda conditions, real tabs, and `__( '...' )` for every user-facing string.
   - Add every new string to **all four** of `lang/en.json`, `es.json`, `fr.json`, and `de.json`, with real translations, not English copies.
5. **Tests.** Every item lists the tests to add or update. Use Pest and follow the existing files in `tests/Feature/**`. After each batch, run:
   ```bash
   php -d memory_limit=1G ./vendor/bin/pest --testsuite=Unit,Feature --compact
   composer lint
   ```
   After Batch A3 the `-d` flag is no longer needed.
6. **Docs.** `docs/` pages, `README.md`, and `CHANGELOG.md` belong to **Batch K**, which happens in the `release/1.0 → main` release PR, not in this fix PR. Inline PHPDoc must be updated with the code, in this PR.
7. Tick the checkbox on each item as you finish it. When you're done, leave this file in place for the release PR to delete. The engine removed its audit doc the same way.

### Never hard-code table names

This is the main rule behind Batch B1. It applies to every change you make.

- Qualify columns through the model:
  - `( new Order() )->qualifyColumn( 'placed_at' )`
  - `$query->qualifyColumn( 'id' )`
  - `$query->getModel()->getQualifiedKeyName()`
- In raw SQL, build the identifier with `$query->getQuery()->getGrammar()->wrap( $model->qualifyColumn( 'quantity_on_hand' ) )`.
- In validation, use `Rule::exists( Model::class, 'id' )` / `Rule::unique( Model::class )`, not `'exists:orders,id'`.
- In tests, use `( new Coupon() )->getTable()` and `$model->getMorphClass()`, never `DB::table( 'coupons' )` or `Product::class` as a morph type.

### B2 · Blocker · `ConfigFormRegistry` misreads engine-declared config schemas
- [x] **Files:** `src/Registries/ConfigFormRegistry.php`:
  - `72` (`TYPES`)
  - `172-185` (`schema()`)
  - `339-381` (`normalize`)
  - `393-420` (`declaredSchema`)
  - `454` (daterange cast)
  - `589-602` (`normalizeOptions`)
- **Problem:** every engine 1.0 built-in now implements `DescribesConfig::configSchema()` (`ArtisanPackUI\Ecommerce\Support\ConfigSchema` / `ConfigField`), and that schema now wins over the admin's `Support/ConfigSchemas`. The admin parses the engine format with its own rules:

  | Engine field | What the admin does | Effect |
  |---|---|---|
  | `'required' => true` | Ignored. Only `'required'` inside `rules` counts. | Required fields become optional. |
  | `help` | Not mapped to `hint`. | Help text is lost. |
  | options `[ 'value' => …, 'label' => … ]` | Only `{id,name}` or scalar maps are kept. | Every select or multiselect gets 0 options, so its rule becomes `Rule::in( [] )`. |
  | `multiple` (engine default `false`) | Admin default is `true`. | Shape is wrong (e.g. `add-free-item.product_id`). |
  | types `variant`, `textarea`, `url`, `list`, `json` | Not in `TYPES`. `normalize` throws and `report()` runs on every `schema()` call. | Log spam. `min-quantity` and `fixed-off-product` fall back to the raw JSON editor. |

- **Verified consequences:**
  - **Weight-based shipping methods cannot be saved:** `c.unit` is reported as invalid.
  - **These promotion conditions cannot be saved:** `cart-contains-category`, `cart-contains-tag`, and `cart-contains-product-type` (match/types), and `currency-is` (with any currency selected).
  - **These kanban triggers cannot be saved** once jobs or providers are configured: `dispatch-job` and `print-shipping-label`.
  - **Required fields are not enforced.** An empty `min-subtotal` amount saves, so does an empty `percent-off-cart` percent, and so does kanban `day-of-week` with no days.
- **Fix:**
  1. In `declaredSchema()`, read `ConfigSchema::of( $entry )` (the engine-normalized form) and adapt each field to the admin shape:
     - `required: true` → prepend `'required'` to `rules`
     - `help` → `hint`
     - options `{value,label}` → `{id,name}`
     - `multiple` defaults to the engine value (`false`)
     - `variant` → `product` with `source => 'variant'`
     - `textarea` → add a `textarea` type (or map it to `template`)
     - `url` → `text` plus a `'url'` rule
     - `list` → `tag`
     - `json` → add a `json` field type, so only that field uses the JSON sub-editor
  2. Add Blade partials for any new types under `resources/views/components/config-form/`.
  3. Never throw for an engine type. Memoize the per-entry result, and `report()` at most once per key per request.
  4. In `WithRuleBuilder::validateRules()` and `WithConfigForms::validateConfigForm()`, also run `\ArtisanPackUI\Ecommerce\Support\ConfigSchema::validate( $entry, $castConfig )` on the cast config before saving. The admin writes `PromotionCondition` / `PromotionAction` / `KanbanAutomation` rows directly (`Promotions/Form.php:339-348`, `KanbanBoards/Automations.php:408-410`), so today nothing engine-side validates them. This also covers kanban routing rules and automation conditions (`KanbanBoards/Edit.php:183-184, 254-264`; `Automations.php:388-389, 558-567`), which reuse the `promotion-condition` registry.
  5. Keep `Support/ConfigSchemas` only for entries that do **not** implement `DescribesConfig`.
  6. Low: an empty `daterange` currently casts to `['start'=>null,'end'=>null]` and is never dropped. Drop it.
- **Tests:**
  - Make the currently failing tests pass:
    - `tests/Feature/ConfigForms/ConfigFormRegistryTest` (including the stale counts: the engine now has 12 conditions and 8 actions)
    - `ConfigFormTest` (tiered-discount, min-subtotal, sibling references)
    - `KanbanBoards/EditTest:94`
    - `Promotions/FormTest` ("validates each row…")
    - `RuleBuilderTest`
    - `Shipping/IndexTest` ("validates the method")
  - Add "adapts every engine-declared schema without throwing". Loop over every key in all five registries. For entries that implement `DescribesConfig`, assert that `schema()` is non-null, select options are non-empty, and `required` fields carry the `required` rule.
  - Add:
    - Shipping: "saves a weight-based method with unit kg and tiers"
    - Promotions: "saves a cart-contains-category condition with match any", "requires percent on percent-off-cart", and "rejects an empty min-quantity.quantity"
    - Kanban: "saves a dispatch-job trigger when jobs are configured"

### B4 · High · License-key search runs `LIKE` against an encrypted column
- [x] **File:** `src/Queries/LicenseKeysQuery.php:99-101` (`orWhereContains( $where, 'license_keys.key', $search )`)
- **Problem:** engine 1.0 casts `key` as `encrypted` and adds `key_hash` (an HMAC of the normalized key; see `LicenseKey::hashFor()` / `hashCandidates()`). So:
  - Searching a real key never matches.
  - A short term can match base64 ciphertext by chance and return unrelated keys.
- **Fix:**
  - When `$searchKeys` is true, use `$where->orWhereIn( LicenseKey::query()->qualifyColumn( 'key_hash' ), LicenseKey::hashCandidates( $search ) )`. That is an exact, normalized, full-key match.
  - Update the search hint or placeholder to say that keys must be entered in full, and add the string to all four lang files.
  - Keep the revoke-only path unable to search by key.
  - Display needs no change: `$key->key` decrypts, and masking still applies.
- **Tests** (`tests/Feature/Livewire/LicenseKeys/IndexTest.php`):
  - The full key, in any case and with any whitespace, finds the row.
  - A partial key does not.
  - A random two-character term returns no keys.
  - A revoke-only user who searches the full key gets no row.

### B7 · High · Engine `AdminMenuRegistry` badges never render, and its sections are dropped
- [x] **Files:** `src/Support/AdminNav.php:294-320` (`registryItems`), `:362-374` (`normalize`), the docblock that still says the registry is "planned for engine 1.0 (#144)"; `src/Livewire/Navigation.php` `render()`; `src/Support/CmsMenu.php` `item()`; `src/Support/NavBadges.php:89-105`.

### C1 · Blocker · `withActionToken` wraps gateway and carrier calls in a DB transaction
- [x] **File:** `src/Livewire/Concerns/WithActionToken.php:94` (`DB::transaction( function () { ActionTokens::consume(...); return $write(); } )`).
- **Callers:**
  - `Orders/RefundsPanel::refund` (`:247`)
  - `Orders/FulfillmentPanel::buyLabel` / `createShipment`
  - `Orders/EditPanel::applyEdit` / `rollbackEdit`
  - `Orders/StatusPanel::cancelOrder`
  - customer and address deletes
  - `Webhooks/Show::replay` (`:166`), which makes an HTTP call when the queue is `sync`
  - `ManagesWebhookSubscriptions` rotate (`:137-139`)
  - `Tax/Index.php:558`, `Shipping/Index.php:670`, `OrderStatuses/Index.php:398`, `KanbanBoards/Columns.php`
- **Problem:** the engine's `RefundService::issue()` and `ShipmentService::buyLabel()` deliberately call the gateway or carrier **outside** any transaction: claim, then external call, then finalize. Wrapping them in an outer transaction causes three failures:
  - The pending-refund row and the order lock are held across the provider's HTTP call.
  - If the gateway declines, the outer rollback erases the `failed` refund row and the `refund.failed` timeline entry.
  - On an amount mismatch, the engine deliberately leaves the refund `pending` to block further refunds. The rollback deletes it, so **money moves at the provider with no ledger row, and the admin can refund again.** A label purchase can be lost the same way.
- **Fix:**
  1. Consume the token first, with its own atomic `insertOrIgnore`. No transaction is needed: the unique index enforces single use.
  2. Run `$write()` without wrapping it in a transaction.
  3. If `$write` throws, delete the consumed `IdempotencyRecord` (same `actor_scope` / `endpoint_key` / `idempotency_key` hash) so the user can retry, then rethrow.
  4. Writers that need atomicity (local-only writes such as tax-class delete and kanban column delete) should open their own `DB::transaction` inside `$write`. Audit every caller listed above, and use `lockForUpdate()` inside it where a check-then-act exists (see F3).
- **Tests:**
  - New `tests/Feature/Livewire/Concerns/WithActionTokenTest.php`:
    - `DB::transactionLevel()` inside `$write` equals the caller's level.
    - A token is still single-use.
    - A throwing `$write` frees the token.
  - `RefundsPanelTest`:
    - A declining gateway leaves exactly one `Refund` with `status=failed` and a `refund.failed` timeline entry.
    - A gateway that returns a mismatched amount leaves a `pending` refund, and a second refund attempt is refused.
  - `FulfillmentPanelTest`: inside the fake provider's `buyLabel`, assert `DB::transactionLevel() === 0`.

## Coverage: checked and fine

These areas were reviewed and need no changes:

- **Authorization:**
  - Every screen authorizes in `mount()`.
  - Every component re-authorizes in `hydrate()`, and every mutating action re-checks the specific ability on the specific record.
  - Client-supplied IDs are scoped to their parent: shipments, refund lines, notes, addresses, variants, gallery images, coupons, deliveries, kanban columns and automations, and notification locales.
  - `#[Locked]` is on every ID and state property that needs it.
  - No mass-assignment paths: settings submit only registry-defined keys, and addresses are intersected with known keys.
- **Action tokens** are HMAC-signed over user + component + action + subject, expire after 12 hours, and are single-use through a unique index (only their transaction scope changes, per C1).
- **Rate limiting:**
  - The limiter detects Livewire updates through `isLivewireRoute()` and throws a 429.
  - `EnsureAdminAccess` is persistent middleware, and Livewire takes the path from the checksummed memo.
- **CSRF and redirects:** CSRF is handled by Livewire, admin routes are GET-only, and there are no open redirects.
- **XSS:**
  - There is no `{!! !!}`, `x-html`, or `innerHTML` anywhere.
  - User data reaches JS through `Js::from`.
  - Email previews render in a `sandbox=""` iframe.
  - URLs are restricted to http(s) (tracking links, review media, product media).
- **Notification templates** render through Twig's `SandboxExtension`. Test sends go only to the acting user and are limited to 5/min.
- **Webhooks:**
  - URLs go through the engine's `WebhookUrlGuard`.
  - The secret is `Str::random(48)` and shown once.
  - Rotate and replay are token-guarded, and replay refuses disabled subscriptions.
- **Settings:** secrets are never rendered back, and changing the base currency needs a confirmation.
- **CSV:**
  - Export guards against formula injection, and import reverses the guard.
  - Reading strips the BOM, sniffs the delimiter, and streams.
  - Imports are UUID-validated and user-scoped, run under a cache lock with per-row transactions, and re-check abilities on every row.
- **ResourceQuery:**
  - Sorts are allow-listed and directions normalized.
  - Filters are normalized against their definitions.
  - `LIKE` searches are escaped.
  - `perPage` is limited to the configured values.
- **Money and inventory:**
  - `MinorUnits` FX conversion matches the engine's `BaseAmounts` (bcmath, rounding half away from zero).
  - Stock adjustments run under `lockForUpdate`.
  - Coupon generation uses `random_int` and catches unique-constraint races.
- **Engine services and APIs called by the admin** all exist with matching signatures on engine main (apart from the items in Batch B). Every engine config key the admin reads exists.
- **Accessibility:**
  - Every button has a label or `aria-label`, and every input has a label.
  - Tables have captions and `scope`.
  - There are level-1 headers and a skip link.
  - Live regions cover result counts, bulk actions, reorders, and broadcasts.
  - Statuses are not shown by colour alone.
  - Drag-and-drop has keyboard alternatives.
  - Focus moves into confirm dialogs and returns afterwards.
- **i18n:**
  - en, es, fr, and de have identical key sets (1,899 each), with no placeholder or plural mismatches and no unused keys.
  - Apart from the items listed above, every user-facing string is wrapped.
- **Packaging:**
  - `VERSION = '1.0.0'` and every `@since` agree.
  - No migrations ship.
  - The publish tags (`ecommerce-admin-config`, `-views`, `-lang`) match the docs.
  - `.gitattributes` export-ignores tests, the workbench, `docs/plans`, and dev files.
  - `.php-cs-fixer.cache`, `node_modules`, and the vendored TinyMCE are untracked.
  - There are no TODO/FIXME comments or debug calls.
- **Livewire 3 and 4:** every API the admin uses exists in both. The JS `request`/`commit` hooks work on Livewire 4.4.7.
